## How to use this log

AI use in this project is required, not banned. Every AI output the team relies
on (a claim we repeat, a citation we include, code we commit, an idea we adopt)
appears here as one row, whether or not it turned out to be correct. Throwaway
drafts we discarded are not logged. This log lives in the root of the repo and
is updated as we work; the commit history shows it growing.

- Total AI outputs logged: **23**    Verified correct: **12**    Failed verification: **11**
  (failed = rows 4-11, 19, 20, 23: 3 CW, 3 MR, 5 OC; no fabricated citations or nonexistent APIs found)
- The two most consequential AI failures (for Task 6, lessons learned):
  - Failure 1: **Row 7 (MR).** The AI's reading of the paper gave Table I's C(1/7) as 218 instead of 2¹⁸ = 262,144, because the PDF text extraction dropped the superscript. Our whole tradeoff comparison is measured against Table I, so this would have made our attacker look over a million times worse than the paper's at α = 1/7, when the real gap is about 1,000 times. Caught because 218 is smaller than the previous entry (4,660), which is impossible for a penalty that grows as memory shrinks.
  - Failure 2: **Row 5 (CW).** Peak-memory code that ran without errors and reported 0 MiB on Linux, because a child process inherits its parent's `ru_maxrss`. Experiment 1's main claim (peak memory equals m) depends on this number. Caught because a memory-hard function using 0 bytes is impossible; fixed by reading `VmHWM` and measuring before any large hash runs.
- Which verification habit saved your team the most time? **Checking every output against an independent reference before building on it:** the RFC 9106 test vectors and intermediate blocks for the code, argon2-cffi for random inputs, and the paper's own numbers for the experiments. The intermediate-block vectors pointed to the exact function at fault whenever something broke.

### F. Lessons learned (Task 6) — Caleb Tyler

**Lesson 1 — A normal watchdog message was incorrectly treated as overheating (v4.3).**

The AI-generated GPU collector originally matched text that included a temperature-abort phrase even when Hashcat was only announcing its configured thermal watchdog threshold. Caleb noticed repeated pauses despite temperatures around 45–50°C, including with other applications closed, and challenged the diagnosis instead of assuming the hardware was overheating. The code was checked against the actual Hashcat startup output and upstream thermal-abort wording. The fix separated real temperature-limit events from normal startup, missing telemetry, timeouts and user pauses; genuine protection remained enabled. The development audit records a regression check against 2,052 historical logs. Caleb subsequently reported successful live collection, pause/resume and preservation of completed measurements. This failure showed that a parser can appear to work in isolated tests yet misinterpret ordinary program output on real hardware. Runtime messages need positive and negative regression cases, and safety mechanisms must not be disabled to hide a software bug.

**Lesson 2 — Multi-GPU metadata was attributed to the wrong device (v4.4).**

The desktop GPU collector worked on the RTX 4090, but the laptop also had Intel integrated graphics. The AI-generated device parser allowed the next OpenCL platform header to overwrite metadata for the selected NVIDIA device. Caleb tested the standalone executable on the laptop and uploaded its failed collection logs. Comparing the device-information log with the actual benchmark/status records revealed the mismatch. The strict identity check rejected the result rather than storing a misleading GPU profile. The corrected parser terminates device records at platform boundaries and retains identity validation. A fresh laptop run saved one correct RTX 3070 Laptop GPU checkpoint (706 H/s, 67°C); the original bad manifest was not reused. This failure showed why cross-hardware tests, explicit device identity checks and raw evidence are essential for an empirical database. A successful benchmark is not useful if its result is attributed to the wrong hardware.

**Additional methodological lesson:** The apparent advantages of AES-GCM and other hybrids in the two-repetition Experiment 7 screening did not survive the seven-round and 500-round verification as improvements over the strongest standalone Argon2. Repeating measurements, freezing the selection, retaining negative results and explicitly distinguishing exploratory findings from confirmed results prevented overstating a noisy performance difference. Similarly, the 32 MiB candidate from Experiment 8 did not establish improved GPU resistance after confirmation. This is why the final contribution is a constrained empirical optimizer, rather than a claim to have invented a universally superior password hashing algorithm.
